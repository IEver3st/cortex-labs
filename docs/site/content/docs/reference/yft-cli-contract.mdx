title: YFT Parser CLI Contract
description: The required behavior for the CodeWalker bridge sidecar that generates .clmesh caches.
---

The app previews `.yft` by parsing fragment data with a CodeWalker-based sidecar and writing a mesh cache (`.clmesh`).

This document defines the required CLI contract for the parser sidecar.

## Executable

- Windows: `CodeWalkerBridge.exe`

The app looks for the binary in:

- Dev: `tools/codewalker-bridge/bin/Release/net10.0/CodeWalkerBridge.exe`
- Dev (fallback): `tools/codewalker-bridge/bin/Debug/net10.0/CodeWalkerBridge.exe`
- Dev: `tools/codewalker-bridge/bin/Release/net8.0/CodeWalkerBridge.exe`
- Dev (fallback): `tools/codewalker-bridge/bin/Debug/net8.0/CodeWalkerBridge.exe`
- Bundled: `<resourceDir>/bin/codewalker-bridge/CodeWalkerBridge.exe`

## Command

```bash
CodeWalkerBridge.exe --input <path-to-yft> --output <path-to-clmesh>
```

## Output

- Writes the mesh cache to the `--output` path.
- Writes `manifest.json` next to the mesh cache.
- Writes exported DDS textures under `textures/` when sibling `.ytd` or embedded textures are available.
- Prints a JSON object to stdout with counts:

```json
{
  "meshCount": 12,
  "vertexCount": 44123,
  "indexCount": 88246,
  "materialCount": 8,
  "textureCount": 19,
  "manifestPath": "C:/Users/.../model-cache/manifest.json"
}
```

## Manifest

`manifest.json` includes exported texture inventory plus per-mesh binding metadata used by the frontend.

- `version` (currently `4`)
- `inputPath`
- `generatedAtUtc`
- `meshCount`
- `textureCount`
- `textures[]`: `name`, `source` (`ytd`, `shared`, or `embedded`), `relativePath`, `nameHash`
- `meshes[]`: `name`, `materialName`, `shaderName`, `shaderHash`, `shaderFileName`, `renderBucket`, `drawableIndex`, `modelIndex`, `lodLevel`, `lodModelIndex`, `geometryIndex`, `uvSets`, `textureBindings`, `textureRefs`, `resolvedTexturePaths`

Each `textureBindings[]` entry includes `paramName`, `textureName`, `relativePath`, `source`, `nameHash`, `usage`, and optional `uvSet`.

Manifest v4 adds `lodLevel` (`high`, `med`, `low`, `vlow`, `extra`, or `unknown`) and `lodModelIndex`. The frontend uses these fields to select the highest available LOD independently for each drawable.

## Mesh cache schema

- Magic: `CLM1`
- Version `1`: positions, optional normals, optional `uv0`, indices
- Version `2`: adds optional `uv1`, `uv2`, and `uv3` payloads after `uv0`

## Exit codes

- `0`: success; output file exists.
- non-zero: failure; app will surface stderr/stdout.

## Output streams

- `stderr`: human-readable progress logs or errors.
- `stdout`: JSON metadata (see above).

## Notes

- The app caches parsed meshes based on input path + modified time + file size plus an internal parser revision. The native-material/LOD contract uses the `parse_yft_v6` revision.
- The `.clmesh` cache is parsed in the frontend into Three.js geometry.
- With Experimental Settings enabled, **All Textures → Native Materials** resolves shader textures from sibling, embedded, resource, and supported shared game YTDs. Manual texture selections override native maps on targeted meshes.
- Advanced dirt/detail/mask bindings that require GTA-specific shader controls are reported as deferred instead of being applied with guessed semantics.
- Frontend texture binding is best-effort Three.js material assignment, not full GTA shader parity.
